# 일본 여행 안전 가이드 (JapanTrip)

한국인 여행자를 위한 일본 여행 앱. **공항 이동 · 교통패스 · 관광지 · 실시간 지진 정보**를
하나로 묶는다. iOS · Android · Web 단일 코드베이스.

현재 버전은 **정보 제공에 집중한다.** 크레딧·기여 보상은 설계와 코드를 갖춰 두되
화면에서 감춰 뒀다 (`src/constants/features.ts`). 보상은 채울 정보가 충분해진 뒤에 열어야
어뷰징이 아니라 기여가 모이기 때문이다.

## 무엇이 다른가

| 기능 | 기존 방식의 문제 | 이 앱의 접근 |
|---|---|---|
| 공항 → 시내 | 노선이 너무 많아 초행자가 못 고른다 | 노선을 큐레이션하고 "추천 / 가장 빠름 / 가장 저렴"을 표시. 오프라인 동작 |
| 교통패스 | 가격만 나열하고 끝난다 | **언제 이득인지 · 뭐가 안 되는지 · 어디서 사는지 · 어떻게 쓰는지** 넷을 함께 적는다 |
| 관광지 | 좋다는 말만 하고 가는 법은 다른 앱을 켜게 만든다 | 가장 가까운 역·노선, 입장료, 권장 소요시간을 함께 담는다 |
| 맛집 평점 | 구글맵은 안 가본 사람도 별점을 남긴다 | GPS 현장 인증을 통과한 리뷰만 평점에 반영 |
| 지진 정보 | 앱을 따로 깔아야 하고 일본어다 | 기상청 발표를 한국어 + 진도별 행동 지침으로 변환 |

## 화면

탭 5개와 상세 화면들로 구성된다.

| 탭 | 내용 |
|---|---|
| 홈 | 안전 상태 요약 · 바로가기 · 지금 자세히 다루는 도시 |
| 공항 | 7개 공항 → 노선별 소요시간·요금 비교, 공항별 함정 |
| 이동 | 도시별 교통패스 6종, IC카드, 현지에서 헷갈리는 것들 |
| 관광 | 30여 곳 · 역/입장료/소요시간, 도시·분류 필터 |
| 안전 | 실시간 지진·긴급지진속보, 비상 연락처 |

상세: `airport/[id]` · `place/[id]` · `roadmap` · `rewards`(비활성)

## 디자인

원칙은 하나다 — **화면이 정보의 위계를 그대로 보여줄 것.** 여행 중 급하게 훑는
화면이라 꾸밈이 늘수록 판단이 느려진다.

- 그림자를 쓰지 않는다. 카드는 배경색 대비(`#F4F5F8`)로만 떠 있다
- 강조색은 인디고(`#4C5FD7`) 하나. 나머지 색은 상태(위험·주의·안전)에만 쓴다
- 여백이 곧 구획이다. 선 대신 간격으로 나눈다
- 모서리를 넉넉히 둥글린다(14~24). 정보 밀도가 높아도 부드럽게 읽히도록
- 카드 왼쪽의 4px 상태 띠가 이 앱의 시각적 표식이다

색 값은 이 앱의 고유 팔레트다. 특정 서비스의 브랜드 색을 그대로 가져다 쓰지 않는다 —
비슷해 보이는 것과 같은 값을 쓰는 것은 다른 문제이고, 후자는 분쟁의 빌미가 된다.

### 말투

설명은 전부 **옆에서 알려주듯** 쓴다. 여행 중에 급하게 읽는 글이라 격식보다 이해 속도가
중요하기 때문이다.

> "이 패스는 교통보다 입장료로 뽑는 거예요. 하루에 유료 관광지를 세 곳 이상 갈 생각이면
> 거의 무조건 이득이고, 지하철만 탈 거라면 오히려 손해예요."

안전 문구도 마찬가지지만, 여기서는 겁을 주지도 안심시키지도 않고 **해야 할 동작만**
앞에 둔다.

> "가구가 움직일 수 있어요. 머리를 감싸고 탁자 아래로 들어가세요. 엘리베이터는 타지 마세요."

코드 주석은 개발자용이라 문어체 그대로 둔다.

**폰트는 Pretendard** — SIL Open Font License 1.1로 배포되는 오픈소스 서체다. 상업 이용을
포함해 자유롭게 쓸 수 있다. 한글과 라틴 문자의 높이가 잘 맞고 숫자 폭이 일정해서 요금·
소요시간을 나열하는 이 앱과 잘 맞는다. Regular·SemiBold·Bold 3종을 번들에 포함했고
(약 7.7MB), 라이선스 전문은 `assets/fonts/Pretendard-LICENSE.txt` 에 함께 배포한다.
앱 안에서도 「정보 → 오픈소스 라이선스」에서 확인할 수 있다.

색·간격·타이포는 `src/constants/theme.ts` 한 곳에서 정의하고, 화면은 `src/components/ui.tsx`
의 컴포넌트만 조합한다. 화면 코드가 색을 직접 만지지 않아야 화면이 늘어나도 한 몸으로
유지된다.

| 용도 | 소스 | 비용 | 상태 |
|---|---|---|---|
| 지진 · 긴급지진속보 | [P2P지진정보 JSON API v2](https://www.p2pquake.net/develop/json_api_v2/) | **무료 · 등록 불필요 · 상업 이용 가능** | 연동 완료 |
| 지진 (대체 경로) | [기상청 JMA](https://www.jma.go.jp/bosai/quake/data/list.json) | 무료 | 검증 완료, 미연동 |
| 공항 · 패스 · 장소 | 자체 큐레이션 | — | 공항 9 · 패스 18 · 장소 108 |

P2PQuake 레이트 리밋은 `/history` 기준 IP당 60회/분. 앱은 60초마다 폴링하고 백그라운드에서는
멈춘다.

### 요금 정보의 신뢰도

교통패스는 개정이 잦아 항목마다 `verified` 플래그를 둔다. 확인하지 못한 값은 금액 대신
「가격 변동 가능 · 판매처 확인」을 띄운다 — 틀린 숫자보다 없는 편이 낫다.

이번 작업에서 확인한 정정 사항:

- 교토 **버스 전용 1일권(700엔)은 폐지**됐다. 아직 그 가격을 안내하는 블로그가 많지만
  지금은 지하철·버스 1일권(1,100엔)이 유일한 대체다
- 오사카 주유패스 1일 3,500엔 / 2일 5,000엔
- 후쿠오카 투어리스트 시티패스 시내 2,500엔 / +다자이후 2,800엔
- 「간사이 스루패스」는 **간사이 레일웨이 패스**로 개명되며 조건이 개정됐다

## 제휴(어필리에이트) 설정

패스 구매 버튼에 추천 코드를 붙여 수수료를 받을 수 있다. 설정은
`src/constants/affiliates.ts` **한 곳만** 고치면 앱 전체에 반영된다.

```ts
klook: {
  referralId: '',   // ← 승인 후 발급받은 ID를 여기에
  ...
}
```

1. 파트너 프로그램에 가입하고 **승인**을 받는다 (승인 전에는 수수료가 잡히지 않는다)
   — [클룩](https://affiliate.klook.com) · [KKday](https://affiliate.kkday.com) · 마이리얼트립 파트너스
2. 발급받은 ID를 `referralId` 에 넣는다
3. 각 패스의 `buyLinks` 에 정확한 상품 URL(`productUrl`)을 넣는다.
   지금은 검색 URL이 기본값이라 링크는 열리지만 상품이 특정되지 않는다

동작 방식:

- `referralId` 가 비어 있으면 **추천 코드 없이** 원본 링크를 연다. 가짜 파라미터를 붙여
  링크를 깨뜨리지 않는다
- 이미 쿼리가 있는 상품 URL에도 안전하게 덧붙는다 (`?spm=abc` → `?spm=abc&aid=...`)
- URL 파싱에 실패해도 원본을 그대로 연다

### 🔴 대가성 표시는 법적 의무

공정거래위원회 「추천·보증 등에 관한 표시·광고 심사지침」상, 수수료를 받는 링크에는
경제적 이해관계를 **명확히** 표시해야 한다. 숨기거나 흐리게 적으면 표시광고법 위반이
될 수 있고 앱스토어 심사에서도 문제가 된다.

그래서 구매 버튼 바로 아래에 `DISCLOSURE` 문구가 항상 붙는다. 추천 ID가 설정된 경우에만
"수수료가 지급돼요" 문구로 바뀌고, 설정 전에는 단순 안내가 나간다. **이 문구를 지우거나
눈에 안 띄게 바꾸지 말 것.**

## 배포

**`main` 에 푸시하면 자동으로 나간다.** (`.github/workflows/deploy-web.yml`)

워크플로가 하는 일은 손으로 하던 것과 같다 — 타입을 검사하고, `npm run build:web` 으로
내보내고, `gh-pages` 브랜치의 내용을 통째로 갈아끼운 뒤 커밋한다. 산출물이 한 글자도
안 바뀌면(README 만 고친 푸시 같은 경우) 커밋하지 않고 조용히 끝낸다.

| | |
|---|---|
| 사이트 | https://abri12.github.io/japantrip/ |
| Pages 설정 | `gh-pages` 브랜치 · 루트 (`build_type: legacy`) |
| 수동 실행 | Actions 탭 → 「웹 배포」 → Run workflow |
| 로컬 빌드만 | `npm run build:web` → `dist/` 확인 |

`actions/deploy-pages` 를 쓰지 않은 이유는 워크플로 머리말에 적어 뒀다. 요약하면
**저장소의 Pages 설정을 사람이 먼저 바꿔야 하는 방식이라, 안 바꾸면 배포가 조용히
멈추기 때문**이다. 지금 쓰는 방식 그대로 자동화하면 바꿀 것이 없다.

린트는 아직 배포를 막지 않는다. `hooks/use-quakes.ts` 에 남은 `set-state-in-effect`
위반 때문인데, 그걸 고치고 나면 워크플로의 「타입 검사」 옆에 `npx expo lint` 를
한 줄 더하면 된다.

## 데이터를 계속 맞게 유지하기

이 앱의 값은 대부분 **남이 정한다.** 요금은 사업자가 개정하고, 첫차는 다이어
개정으로 움직이고, 가게는 문 여는 시간을 바꾼다. 코드가 멀쩡해도 데이터는
가만히 있는 채로 틀려 가는데, 테스트도 타입 검사도 그건 못 잡는다.

「확인하지 않은 값은 넣지 않는다」의 운영판이 아래 셋이다.

### 항목마다 확인 시점을 단다

교통패스와 공항에 `checkedAt`(`'2026-08'`)이 있다. 예전에는 파일 전체를
대표하는 상수 하나였는데, 그러면 패스 하나만 갱신해도 열여덟 개가 전부
「방금 확인함」으로 보이고 반대로 하나가 낡아도 화면은 최신인 척했다.
지금은 갱신한 것만 날짜가 움직이고, 낡은 것은 낡은 채로 드러난다.
화면(패스 카드)에도 항목별로 나간다.

### 다시 볼 것을 스크립트가 뽑는다

```bash
npm run audit:data
```

| 보는 것 | 기준 |
|---|---|
| 확인이 오래된 항목 | 패스·공항 `checkedAt` 6개월 |
| 확인 못 한 값 | `verified: false` |
| 코드에 남긴 재확인 표시 | 주석의 「재확인이 필요」 |
| 지나간 개정 예정일 | `KNOWN_REVISIONS` |

조사 중에 「언제부터 바뀐다」를 알게 되면 스크립트의 `KNOWN_REVISIONS` 에
적어 둔다. 기억에 맡기면 반드시 놓친다. 반영이 끝나면 지운다 — 남겨 두면
매달 같은 항목이 떠서 목록 전체를 흘려보게 된다.

**실패시키지 않는다.** 데이터가 낡은 것은 버그가 아니라 할 일이라, 배포를
막으면 급한 수정을 못 내보내게 되고 결국 이 검사를 꺼 버린다.

### 매달 스스로 물어본다

`.github/workflows/data-audit.yml` 이 매달 1일에 위 스크립트를 돌려
**결과를 이슈로 남긴다.** 화면 로그로만 흘리면 아무도 안 본다. 볼 게 없으면
이슈를 만들지 않는다 — 「할 일 없음」이 쌓이면 진짜 이슈가 그 사이에 묻힌다.

확인을 마쳤으면 그 항목의 `checkedAt` 을 이번 달로 옮긴다. 그게 다음 달
점검의 기준이 된다.

## 화면이 실제로 그려지나

```bash
npm run build:web && npm run check:screens
```

`expo export` 는 화면을 **미리 그려서** HTML 로 낸다. 그래서 브라우저를 띄우지
않고도 파일을 열어 글자가 있는지 보는 것만으로 「이 화면이 내용을 그렸나」를
알 수 있다. 이 앱에서 가장 나쁜 실패가 흰 화면이라, 매 배포마다 확인한다.

### 화면이 세 종류다

미리 그리는 시점에는 저장소도 네트워크도 없다. 한 잣대로 재면 멀쩡한 화면이
실패로 잡히므로 나눠 본다.

| 종류 | 무엇 | 무엇을 보나 |
|---|---|---|
| static | 공항·이동수단·관광처럼 데이터가 앱 안에 있는 화면 | 글자 수 + 반드시 있어야 할 말 |
| stateful | 홈·날씨·내 일정처럼 고른 도시나 저장값이 있어야 하는 화면 | **빈 상태 안내**가 제대로 나오는지 |
| dynamic | `airport/[id]` 처럼 파라미터가 필요한 화면 | 검사하지 않는다 |

글자 수만 보면 「제목만 그려지고 본문이 비었다」를 못 잡는다 — 며칠째 선택이
1일차만 나오던 버그가 그런 모양이었다. 그래서 화면마다 있어야 할 말을 적어 둔다.

### 못 보는 것

**눌러야 나오는 것.** 거점을 고르고 다음 화면으로 넘어가는 흐름은 안 보인다 —
후쿠오카 공항에서 나리타 시각이 나오던 버그가 그런 종류였다. 이 검사는 바닥을
받치는 것이지 천장이 아니다.

### 상세 화면도 미리 그린다

`/place/dotonbori` 같은 주소는 예전에 내보내기에 없었다. 정적 호스팅이
`404.html` 을 주는데 그 안에는 내용이 없으니 리액트가 붙일 것이 없고,
**하이드레이션이 어긋나 React #418 이 떴다.** 화면은 그려지지만 한 번
깜빡이고, 미리 그리는 이점이 통째로 사라진다.

라우트 셋에 `generateStaticParams` 를 붙여 125개(장소 108 · 공항 9 · 코스 8)를
주소마다 내보낸다. 무엇을 그릴지는 **`src/data/static-routes.ts` 한곳**에서
정한다 — 라우트 파일마다 「전부 다」를 적으면 정책이 세 곳으로 흩어진다.

#### 늘어날 것을 전제로 둔 장치

| | 지금 | 왜 |
|---|---|---|
| 상한 | 400개 | 넘으면 **빌드 로그로 알리고** 넘긴다. 조용히 느려지는 것이 가장 나쁘다 |
| 제목 | 데이터에서 뽑음 | 표에 한 줄씩 적으면 장소 하나 더할 때마다 빌드 스크립트를 고쳐야 한다 |
| 화면 점검 | 무리 규칙 | 108개를 목록에 적지 않고 `place/` 로 묶어 같은 잣대로 잰다 |

상한에 걸린 화면은 예전처럼 404 폴백으로 뜬다 — 동작은 하고 깜빡일 뿐이라
안전한 쪽으로 내려앉는다.

#### 크기는 왜 그냥 두나

HTML 한 장이 39KB 이고 그중 20KB 가 **페이지마다 반복되는 인라인 CSS** 다.
빼서 공용 파일로 만들고 싶어지는 모양인데, 그러면 **오히려 느려진다.**

이 앱은 SPA 라 사용자가 HTML 을 **한 장만** 받는다. 그 뒤 화면 이동은 전부
클라이언트 라우팅이라 HTML 을 다시 안 받는다. CSS 를 별도 파일로 빼면 첫
화면에 왕복이 하나 더 생기고, 두 번째 페이지는 애초에 없다.

실제로 오가는 양은 **gzip 후 한 장에 9KB** 다(154장 합계 1.4MB). 저장소 쪽도
같은 내용의 파일이라 git 이 잘 묶는다. 지금 구조가 맞다.

장소가 1,000개쯤 되면 다시 볼 값이다 — 그때는 상한이 먼저 말해 준다.

## 값은 서버가 정한다

교환 요청이 이랬다.

```
POST /api/credits/redeem  { rewardId: 'starbucks', cost: 3000 }
```

서버가 그 `cost` 를 그대로 믿고 차감했다. 즉 **클라이언트가 자기 값을 정했다** —
`cost: 1` 이면 1크레딧으로 3,000짜리 기프티콘이 나간다. 앱을 고칠 필요도 없이
주소로 요청 한 번이면 된다.

원장을 서버로 옮기고(기기가 잔액을 못 만들게), 출금 게이트를 세우고(한 사람이
한 사람분만 받게), 발행 한도까지 둔 것이 **이 한 줄로 전부 무의미해지는**
자리였다. 잔액을 못 만들어도 값을 1로 부르면 그만이니까.

지금은 요청이 **무엇을 바꿀지(`rewardId`)만** 말한다. 얼마인지는
`server/rewards.mjs` 가 자기 표에서 찾고, 요청이 보낸 `cost` 는 **읽지 않는다** —
검사만 해도 「맞으면 통과」라는 여지가 남는다.

### 표는 앱 데이터에서 뽑는다

```bash
npm run gen:rewards   # 보상 목록을 고쳤으면 다시 돌린다
```

원본은 `src/lib/credits.ts` 하나다. 거기에 이 경제를 왜 이렇게 짰는지가 전부
적혀 있어서, 값만 따로 떼면 맥락이 끊긴다. `gen-places-geo.mjs` 와 같은 방식이고,
`check:shared` 가 뽑은 뒤에 원본만 고치지 않았는지 본다.

### 조회 하나에도 함정이 있었다

`REWARDS[id]` 로만 찾으면 **물려받은 속성이 걸린다.** `id` 가 `'toString'` 이면
함수라서 참이고, 그다음 `.cost` 가 `undefined` 로 나온다. 호출부가 `null` 만
막고 있으면 그게 지나가서 원장에 `delta: -undefined` 즉 **NaN 이 기록된다.**
잔액 계산이 통째로 무너진다.

그래서 문자열일 것과 `Object.hasOwn` 을 둘 다 강제한다. 원장에 NaN 이 들어가면
되돌릴 방법이 없어서 호출부에도 `Number.isInteger` 검사를 한 겹 더 뒀다.

### 서버가 없으면 교환하지 않는다

다른 기능은 서버가 없으면 기기에서 처리하고 넘어간다(날씨·지진). 교환은 그러면
안 된다. 크레딧은 지급 의무가 생기는 값이라, 기기가 자기 잔액을 깎고 「완료
됐어요」라고 말해도 실제로 나가는 것은 아무것도 없다 — 사용자는 받은 줄 알고
기다리게 된다. 여기만은 실패를 그대로 말하고 잔액도 건드리지 않는다.

## 서버가 파일에 안전하게 쓰는 법

서버는 상태를 JSON 파일에 담는다(원장·출금·기여·리뷰·구독자·오류). 여섯
모듈이 각자 저장 코드를 들고 있었는데, 그 코드가 이랬다.

```js
await writeFile(FILE, JSON.stringify(db), 'utf8');
```

문제가 둘이다.

| | 무슨 일이 나나 |
|---|---|
| 쓰는 도중 종료 | `writeFile` 은 파일을 먼저 비우고 채운다. 그 사이 죽으면 **반쪽 JSON** 이 남고, 다음 실행에서 파싱이 실패해 모듈이 「첫 실행」으로 넘어간다 — **잔액이 0이 된다** |
| 1초 안에 종료 | 저장을 1초 미뤄 몰아 쓰는데, 그 안에 끄면 마지막 변경이 사라진다 |

### 임시 파일에 쓰고 이름을 바꾼다

`server/store.mjs` 의 `saver()` 가 그 일을 한다. 이름 바꾸기는 파일 시스템이
쪼갤 수 없는 한 동작이라, 어느 시점에 죽든 파일은 **옛 내용이 온전하거나 새
내용이 온전하거나** 둘 중 하나다. 반쯤 쓰인 상태가 존재하지 않는다.

여섯 모듈이 같이 쓴다. 각자 두면 이 수정도 여섯 번 해야 하고, 다음에 하나를
빠뜨린다 — 이 저장소에서 같은 규칙이 두 벌로 갈라져 사고가 난 적이 이미 두 번
있었다.

### 돈은 미루지 않는다

원장과 출금은 `store.schedule()` 이 아니라 **`saveNow()` 로 그 자리에서** 쓴다.
리뷰가 1초 늦게 저장되는 것과 크레딧이 사라지는 것은 무게가 다르다.

종료 신호를 받으면 밀린 저장을 마저 쓰는 장치도 있지만(`flushAll`), 그건
**신호를 받을 수 있을 때만** 통한다 — 전원이 나가거나 강제 종료되면 안 돌고,
윈도우에서는 다른 프로세스가 보낸 신호가 그렇게 전달되지 않는다. 지킬 수 있는
것에만 기댄다.

확인 방법: 지급 직후 `SIGKILL` 로 강제 종료해도 원장이 파일에 남는다. 예전
방식으로 되돌리면 같은 시험에서 지급이 사라진다.

## 앱과 서버가 말을 맞추고 있나

앱은 React Native, 서버는 순수 Node 다. 빌드를 같이 하지 않으니 코드를 공유할
방법이 없고, 그래서 **같은 값을 양쪽에 각각 적어 둔 자리**가 있다. 두 파일은
서로를 임포트하지 않으니 타입 검사에게는 남남이다.

어긋나면 증상이 고약하다 — **앱은 통과인데 서버는 거부**하는 상태가 되고,
사용자는 앱이 「인증됨」이라 해 놓고 저장이 안 되는 걸 본다.

```bash
npm run check:shared
```

| 규칙 | 내용 |
|---|---|
| A | `SHARED` 에 등록한 값이 양쪽에서 같은가 (정확도 상한 65 · 기본 반경 10) |
| B | 서버가 돌려주는 거부 사유를 앱이 전부 사람 말로 옮기는가 |

B가 더 자주 깨진다. 서버에 사유를 하나 더하는 것은 쉽고, 앱의 `switch` 를 같이
고치는 것은 잊기 쉽다. 잊으면 사용자가 「잠시 뒤에 다시 시도해주세요」를 보는데
다시 시도해도 안 된다. 화면으로는 만들 수 없는 사유(별점 범위 등)는 `GENERIC_OK`
에 **이유와 함께** 올려서 일반 문구로 떨어뜨린다.

값을 두 곳에 적는 순간 `SHARED` 에도 한 줄 적는다 — 등록하지 않으면 스크립트가
모른다.

## 서버 테스트

```bash
npm test        # node --test, 의존성 없음
```

여섯 파일 93개. 프레임워크를 안 쓴 이유는 서버가 이미 Node 내장만으로 돌기
때문이다. 러너가 **파일마다 별도 프로세스**로 돌려서 모듈 상태도 저절로
격리된다.

원장·출금·리뷰는 파일 경로를 모듈 최상단에서 환경변수로 읽는다. 그래서 임포트
지정자에 쿼리를 붙여(`import('../ledger.mjs?t=3')`) 모듈을 새로 평가시키는
방식으로 시나리오마다 빈 상태를 연다(`server/test/helpers.mjs`). 소멸·FIFO·이동
속도처럼 **시각에 기대는 계산**은 실제 시계로는 못 짜니, 날짜를 박은 파일을
심어 두고 읽는다.

⚠ 이 수법은 직접 임포트하는 모듈에만 통한다. `payout.mjs` 안의
`import './ledger.mjs'` 는 쿼리 없는 지정자라 캐시된 원장을 본다.

## 화면이 누구 이야기를 하고 있나

타입 검사도 린트도 못 잡는 오류가 한 종류 있다. 이 앱에는 **답이 갈리는 두
출처**가 있어서다.

| 출처 | 어디서 오나 |
|---|---|
| 고른 도시 | 저장돼 있고 앱 어디서나 읽힌다 (`useSelectedCity`) |
| 지금 보고 있는 화면 | 라우트 파라미터 (`/airport/fuk`) |

대부분의 화면은 앞쪽만 쓴다. 그런데 공항 탭에 「전체 보기」가 있어서, 도쿄를
고른 사람도 후쿠오카 공항을 열어 볼 수 있다. 그 화면에서 앞쪽을 읽으면
후쿠오카 화면이 나리타 답을 한다.

실제로 그랬다. 후쿠오카 공항에서 「몇 시에 숙소를 나서야 하나요」를 누르면
**나리타 기준 「비행기 4시간 20분 전」**이 나왔다 — 후쿠오카는 2시간 55분인데.
방향이 반대면 1시간 25분을 **모자라게** 답한다. 되돌릴 수 없는 날에.

두 값 다 타입이 맞고 문법도 맞다. 틀린 건 **어느 쪽을 읽어야 하는가**뿐이라
컴파일러가 볼 수 있는 게 없다.

### 화해시키는 자리를 하나로 둔다

`src/lib/airport-context.ts` 의 `useAirportContext` 가 그 자리다. 규칙은 셋.

1. 화면이 공항을 들고 있으면(`airportId`) **그쪽이 이긴다.**
2. 그 공항이 고른 도시의 공항이 **아니면** 도시에 매달린 값을 아예 안 쓴다 —
   저장된 거점 id · 도시 이름 · `hubForCity` 의 도시 기준까지.
3. 화면이 공항을 안 들고 있으면 고른 도시의 공항으로 떨어진다.

버그가 났을 때 화면 두 곳(`use-airport-detail` · `use-departure-plan`)이
**같은 규칙을 따로 구현**하고 있었다. 한 곳만 고치면 다른 곳이 남고, 새 화면이
생기면 세 번째 구현이 생긴다. 규칙을 한곳에 모은 이유가 그거다.

### 우회하면 배포가 막힌다

```bash
npm run check:context
```

| 규칙 | 내용 |
|---|---|
| A | `useSelectedCity` 는 스크립트의 `MAY_READ_SELECTED_CITY` 에 오른 파일만 부를 수 있다 |
| B | 라우트 파라미터를 읽는 화면은 `useSelectedCity` 에 닿으면 안 된다 (임포트를 타고 간접으로도). 통과하는 문은 `lib/airport-context.ts` 하나뿐 |

목록에 오른 것들은 전부 「이 화면의 주제가 곧 고른 도시」인 곳이고, 항목마다
**이유가 적혀 있다.** 새 화면이 규칙을 어기면 목록에 없으므로 걸리고, 정당한
예외라면 이유를 적으면서 올리게 된다. 그 강제가 이 스크립트의 본체다.

`audit:data` 와 달리 **실패시킨다.** 저쪽은 데이터가 낡은 것이라 할 일에
가깝지만, 이쪽은 코드 구조의 불변식이고 답이 결정돼 있다. 배포 워크플로의
타입 검사·린트 옆에서 같이 돈다.

## 인증 반경 — 왜 10m를 그대로 쓰지 않는가

기본 반경은 10m다. 다만 이 값을 거리와 그대로 비교하면 **진짜 방문자가 대량 탈락한다.**

- 스마트폰 GPS 오차는 개활지에서 약 5m지만, 도심 고층가에서는 20~50m, **실내에서는 그
  이상**으로 벌어진다. 리뷰를 쓰는 시점은 대개 가게 안이다
- 반대로 반경을 좁혀도 **위조는 못 막는다.** 모의 위치 앱은 좌표를 정확히 찍으므로
  반경이 10m든 300m든 똑같이 통과한다

그래서 두 가지를 둔다:

1. **기기 정확도를 반경에 더한다** — `거리 ≤ 반경 + accuracy`. 단 정확도가 65m를 넘으면
   판정을 거부한다(큰 오차를 핑계로 통과하는 것을 막는다)
2. **장소별 반경**(`Place.radiusM`) — 오도리공원 400m, 후시미이나리 300m, 츠키지 120m,
   작은 식당은 기본 10m. 좌표는 한 점이지만 시장·공원은 수백 m다

정보 제공만 하는 지금 단계에서는 충분하지만, **크레딧을 켜기 전에는 반드시 원장을 서버로
