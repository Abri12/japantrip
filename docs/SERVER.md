# 서버

> **읽기 프록시는 만들었다.** `server/` 에 있고 `npm run server` 로 뜬다.
> 상태를 다루는 것(크레딧·리뷰·푸시)은 아직 계획 단계다 — 아래 표에서 갈린다.

## 지금 돌아가는 것 — 읽기 프록시

앱이 외부 API 를 **기기에서 직접** 부르면 세 가지가 동시에 막힌다.
키를 앱에 넣을 수 없어 무료·무키 소스만 쓰게 되고, 호출 수가 사용자 수만큼
늘어나 한도가 터지고, 소스를 바꾸려면 앱을 새로 배포해야 한다.

그래서 **운영자가 서버에서 한 번 부르고 모두에게 나눠 준다.** 호출 수가
사용자 수가 아니라 **시간**에 비례하는 것이 핵심이다.

| 엔드포인트 | 업스트림 | 캐시 | 서버를 두는 이유 |
|---|---|---|---|
| `/api/fx` | Open Exchange Rates → ExchangeRate-API → ECB | 1시간 | **시간당 갱신 소스는 키가 필요**한데 앱에 넣으면 노출된다. 무키 소스는 전부 하루 1회라 환율 변동이 큰 시기에 값이 벌어진다 |
| `/api/weather` | Open-Meteo | 10분 | 같은 도시면 답이 같다. 좌표를 소수점 2자리(약 1km)로 끊어 도시 단위로 묶는다 |
| `/api/warning` | 기상청(JMA) | 5분 | 지역코드가 같으면 답도 같다. 기상청이 요구하는 「과도한 접근 자제」에도 맞는다 |
| `/api/quakes` | P2PQuake | 1분 | **IP당 60회/분** 제한. 공용 와이파이처럼 IP 를 공유하면 여럿이 한꺼번에 막힌다 |
| `/api/train-status` | JR서일본 | 2분 | 간사이권(오사카·교토) |
| `/api/train-status/odpt` | 공공교통 오픈데이터 | 2분 | 도쿄권. 키 없이 도에이, 키를 넣으면 메트로·JR동일본까지 |

### 운행정보는 왜 도시마다 다른가

철도는 **회사마다 공개 정도가 다르다.** 조사한 결과가 이렇다.

| 소스 | 키 | 받는 것 |
|---|---|---|
| JR서일본 `area_{code}_trafficinfo.json` | 불필요 | 간사이·호쿠리쿠·오카야마·히로시마·산인 |
| ODPT `api-public.odpt.org` | **불필요** | 도에이 지하철 6개 노선 |
| ODPT `api.odpt.org` | 필요 | 도쿄메트로·JR동일본까지 |
| JR동일본 자체 페이지 | — | 외부 접근 차단(403) |

키 없는 도에이만으로도 값지다 — **아사쿠사선이 하네다·나리타 양쪽으로
이어지고 오에도선이 신주쿠를 지난다.** 이 앱의 공항 경로가 그 위에 있다.

나머지 도시는 그 도시를 담당하는 회사의 **공식 운행정보 페이지로 보낸다**
(`src/data/train-status.ts`). 없는 것을 있는 척하느니 어디를 봐야 하는지라도
정확히 아는 편이 낫다 — 태풍·폭설 때 여행자는 일본어로 회사 이름부터 찾아
헤매는데, 그 시간이 사라지는 것만으로도 값지다.

### ODPT 키를 넣으면 도쿄권 전체로

개발자 등록은 **무료이고 상업 이용도 허용**된다(2022년 이후).
계정 발급은 이메일 인증이 필요해서 사람이 직접 해야 한다.

1. https://developer.odpt.org 에서 개발자 등록 (평일 오전 기준 45분 내 승인 메일)
2. 로그인 후 액세스 토큰 발급
3. `.env` 에 `ODPT_TOKEN=발급받은키` 를 적는다
4. `npm run check:odpt` 로 확인

서버는 `.env` 를 스스로 읽으므로 명령 앞에 붙일 필요가 없다. 키를 명령줄에
쓰면 셸 히스토리에 남는데, 파일에 한 번 적어 두는 편이 안전하고 덜 번거롭다.

```
$ npm run check:odpt

키 없이 (api-public): 노선 6개
   도에이 지하철        6개 노선

키 사용 (api.odpt.org): 노선 NN개
 + 도쿄메트로          9개 노선
 + JR 동일본           NN개 노선

키가 동작해요 — 사업자 2곳 · 노선 NN개가 늘었어요.
앱이 도쿄에서 쓰는 세 사업자가 모두 잡혀요.
```

**왜 점검 스크립트가 따로 필요한가** — 평상시에는 전 노선이 「지연 없음」이라
키가 있든 없든 화면이 똑같이 조용하다. 화면만 봐서는 넓어졌는지 알 수 없어서,
사업자와 노선 수를 직접 세어 보여준다. 잘못된 키는 HTTP 403 으로 구분해
「토큰을 다시 확인하세요」라고 말한다.

화면은 키 유무를 몰라도 된다 — 실제로 값이 온 사업자만 「앱이 자동으로
확인하는 곳」이라 적고, 안 온 곳은 링크로 남는다. 키가 없을 때 「자동
확인 중」이라고 말하면 그건 거짓말이 된다.

### 지켜야 할 규칙 — 서버는 전제가 아니다

모든 호출부가 같은 모양이다: **서버를 먼저 부르고, 실패하면 공개 API 로 떨어진다.**
(`src/lib/api.ts` 의 `fromServer()`)

서버가 죽었다고 날씨 화면이 비면, 사용자에게는 앱이 고장난 것이지 서버가
죽은 게 아니다. 여행 중에 그건 치명적이다. 서버는 **한도와 성능을 위한
것**이지 기능의 조건이 아니다.

### 실행

```bash
npm run server                                        # 키 없이 (무료 소스)
OPEN_EXCHANGE_RATES_APP_ID=xxx npm run server         # 환율 시간당 갱신
PORT=8080 ALLOWED_ORIGIN=https://abri12.github.io npm run server
```

앱 쪽은 `EXPO_PUBLIC_API_BASE` 하나만 주면 된다. 없으면 예전처럼 공개 API 직통이다.

```bash
EXPO_PUBLIC_API_BASE=http://192.168.0.10:8787 npm run web
```

> ⚠ `EXPO_PUBLIC_` 이 붙은 값은 **앱 번들에 그대로 들어간다.** 여기 두는 건
> 공개해도 되는 주소뿐이고, API 키는 서버 환경변수로만 존재해야 한다.

## 지진 푸시 — 만들었다

앱을 켜야만 지진을 아는 구조로는 긴급지진속보가 쓸모없다. 흔들림 도달까지
수 초~수십 초가 전부다. 그리고 P2PQuake WebSocket 은 **IP당 동시 2연결**이라
기기마다 붙을 수도 없다. 서버가 연결 하나를 들고 상주한다.

```
P2PQuake WebSocket ──▶ server/quake-watch.mjs
                          │  ① 내가 있는 현에 해당하나
                          │  ② 사용자가 정한 진도 이상인가
                          │  ③ 이미 알린 지진 아닌가
                          ▼
                       Expo Push ──▶ 대상자만
```

| | |
|---|---|
| 등록 | `POST /api/push/register` — `{token, pref, minScale}` |
| 해제 | `POST /api/push/unregister` — `{token}` |
| 명부 | `.data/subscribers.json` (토큰·도도부현·최소진도만) |
| 감시 끄기 | `QUAKE_WATCH=off` — 서버를 여러 개 띄울 때 2연결 제한 회피 |

### 알림을 줄이는 두 겹

일본에는 사람이 못 느끼는 지진이 하루에도 여러 번 있다. 다 보내면 사용자가
알림을 통째로 꺼 버리고, 그러면 **정작 위험할 때도 못 받는다.**

1. **내가 있는 현만** — 규슈 지진을 도쿄 여행자에게 보내지 않는다
2. **진도 4 이상만** — 그 아래는 알림을 받아도 할 일이 없다

긴급지진속보만 방해금지를 뚫는다(안드로이드 `eew` 채널, iOS critical).
자고 있어도 깨워야 하는 유일한 종류라서다. 지난 지진 정보는 `quake` 채널로
따로 두어, EEW 를 끄려다 전부 꺼지는 일이 없게 한다.

### 저장하지 않는 것

좌표·이동 이력·계정을 받지 않는다. **토큰 · 도도부현 · 최소진도** 셋뿐이다.
도도부현은 사용자가 고른 도시에서 그대로 나오는 값이라 위치 권한도 필요 없다.

### 웹에서는 동작하지 않는다

Expo 푸시는 네이티브 빌드에서만 된다. 웹에서는 권한도 묻지 않고 조용히
건너뛴다 — 아무 소용 없는 권한 창으로 사용자를 놀래지 않는다.

### 무료 등급 계산

Open Exchange Rates 무료는 월 1,000회다. 시간당 1회면 **월 720회**라 그대로
들어간다. 사용자가 10명이든 10만명이든 같다 — 기기가 직접 부르면 사용자
30명만 돼도 첫날 한도가 터진다.

## 1. 크레딧 원장 🔴

**지금** — `loadProfile()` / `award()` 가 AsyncStorage의 `profile:v1` 을 직접 읽고 쓴다.
잔액도 누적 획득량도 기기 안에만 있다.

**왜 옮겨야 하나** — 저장소를 직접 고치면 크레딧을 무한히 만들 수 있다. 크레딧은 eSIM·
티켓 할인으로 교환되는, 즉 **금전적 가치가 있는 잔액**이다. 클라이언트가 자기 잔액을
계산하는 구조로는 절대 켜면 안 된다.

**서버가 맡을 것**
- 잔액·누적 획득의 유일한 사본(single source of truth)
- 지급/차감을 추가 전용 원장(append-only ledger)으로 기록 — 사후 감사 가능해야 한다
- 교환(`redeem`)은 멱등 처리 — 네트워크 재시도로 이중 차감이 나면 안 된다

**클라이언트에 남길 것** — 표시용 캐시. 화면이 잠깐 옛 잔액을 보여주는 건 괜찮다.

## 2. 기여 교차검증 🔴

**지금** — `confirmContribution()` 이 로컬 배열의 카운터를 올리고, 임계치에 닿으면
`status`를 `confirmed` 로 바꾸며 크레딧을 지급한다. **같은 기기에서 자기 제보를 자기가
확인할 수 있다.** 지금은 단일 기기 시뮬레이션이라 그렇게 열어 뒀다.

**왜 옮겨야 하나** — 교차검증은 "다른 사람이 확인했다"는 사실 자체가 전부인 장치다.
그 판정이 제보자 기기 안에 있으면 아무 의미가 없다.

**서버가 맡을 것**
- 제보자 ≠ 확인자 강제, 확인자 1인 1회 제한
- 확정 판정과 그 시점의 크레딧 지급 (원장과 같은 트랜잭션 안에서)
- 등급별 요구 확인 수 계산 — `confirmationsRequired()` 를 서버로 옮긴다
- 반려 누적 시 제재 (현재 설계에 없음. 추가 필요)

**남는 문제** — 여러 계정을 만들어 서로 확인해 주는 담합은 이 구조로 못 막는다.
계정 생성 비용(전화번호 인증 등)과 이상 패턴 탐지가 별도로 필요하다.

## 3. GPS 인증 판정 🟠

**지금** — `checkProximity()` 가 기기에서 거리와 정확도를 계산해 통과 여부를 정한다.

**왜 옮겨야 하나** — 앱을 거치지 않고 API를 직접 호출하면 "인증됨" 상태를 그냥 만들어
보낼 수 있다. 리뷰가 내 기기에만 남는 지금은 무해하지만, 남에게 보이는 순간 문제가 된다.

**서버가 맡을 것**
- 좌표·정확도를 받아 **서버가 다시 판정**한다. 클라이언트 판정 결과는 참고만 한다
- 장소 좌표와 `radiusM` 은 서버 데이터를 기준으로 한다 (앱 내장본은 표시용)
- 같은 사용자가 짧은 시간에 멀리 떨어진 두 곳을 인증하면 거부 — 물리적으로 불가능한
  이동은 위치 위조의 가장 잡기 쉬운 신호다

**주의** — 서버로 옮겨도 모의 위치 앱은 못 막는다. 판정 위치를 옮기는 것은 *API 우회*를
막는 것이지 *위치 위조*를 막는 게 아니다. 둘은 다른 문제다.

## 4. 리뷰 저장소 🟠

**지금** — `reviews:v1` 키에 로컬 저장. 앱을 지우면 사라지고, 남에게 보이지 않는다.

**서버가 맡을 것**

- 신고·삭제 처리
- **인증 리뷰만 평균에 반영**하는 규칙은 서버에서 강제한다. 이 앱 평점의 존재 이유다

## 5. 지진 푸시 알림 🟠

**지금** — `use-quakes.ts` 가 60초마다 P2PQuake `/history` 를 폴링한다. 앱이 백그라운드로
가면 멈춘다.

**왜 옮겨야 하나** — 앱을 켜야만 지진을 아는 구조는 위급 정보로서 쓸모가 없다.
긴급지진속보는 흔들림 도달 전 수 초~수십 초가 전부다.

**왜 클라이언트가 직접 못 하나** — P2PQuake WebSocket(`wss://api.p2pquake.net/v2/ws`)은
**IP당 동시 2연결** 제한이 있다. 사용자마다 직접 붙을 수 없다.

**서버가 맡을 것**
- WebSocket **1개 연결**로 구독 → 이벤트를 받아 저장
- 사용자의 체류 도도부현과 대조해 대상자만 추려 Expo Push 로 팬아웃
- 진도 임계치(예: 진도 4 이상)와 EEW는 다른 채널로 — 모든 지진을 알리면 알림을 꺼 버린다
- 폴링은 WebSocket 끊김 대비 fallback 으로 유지

## 6. 큐레이션 데이터 배포 🟡

**지금** — 공항·패스·장소가 전부 앱에 하드코딩. 요금이 바뀌면 **앱을 새로 배포해야 한다.**

**옮길 때** — 서버에서 JSON 을 내려받아 캐시하고, 앱 내장본은 **오프라인 fallback** 으로
남긴다. 공항 화면이 데이터 로밍 없이 열리는 건 이 앱의 장점이라 없애면 안 된다.

관련: `data/transit.ts` 의 `verified` 플래그와 `PASS_CHECKED_AT` — 서버로 옮기면
확인 시점을 항목별로 관리할 수 있다.

## 먼저 정해야 할 것

서버를 붙이기 전에 답이 필요한 것들이다. 기술 선택보다 이게 먼저다.

1. ~~**계정을 만들 것인가**~~ — **안 만들기로 했다.** 이 앱은 「회원가입이 없다」를
   지켜 왔고 리뷰 하나 때문에 그걸 버릴 이유가 없다. 기기가 만든 임의의 id 로
   「내가 쓴 리뷰」만 구분한다. 담합은 못 막지만, 리뷰는 **현장에 가야 쓸 수
   있어서** 그 비용이 실제 이동이다.
2. ~~**위치를 서버에 보낼 것인가**~~ — **보내되 저장하지 않기로 했다.** 판정에
   쓰고 즉시 버린다. 리뷰에 남는 것은 「인증됨」과 거리뿐이다. 예외는 직전 인증
   한 건의 좌표·시각 — 물리적으로 불가능한 이동을 잡는 데 필요하고, 다음 인증이
   오면 덮어써서 이력이 되지 않는다.
3. **크레딧의 법적 성격** — 현금성 포인트로 보이면 규제 대상이 될 수 있다. 기프티콘
   전환을 넣는다면 이 검토가 선행되어야 한다. **아직 안 했다.**

## 크레딧

원장·교차검증에 더해 **담합 방지와 발행 한도**까지 서버로 옮겼다.

| 모듈 | 하는 일 |
|---|---|
| `ledger.mjs` | 추가 전용 원장. 잔액은 합으로 낸다. 멱등 |
| `contributions.mjs` | 교차검증. 머릿수가 아니라 **무게**를 센다 |
| `anti-collusion.mjs` | 현장·상호성·집중도·동일망으로 확인의 무게를 정한다 |
| `payout.mjs` | 출금 게이트. 수령처 유일성 · 숙려 · 기간 상한 |
| `issuance.mjs` | 전자금융거래법 등록 면제선을 넘지 못하게 막는다 |

설계 근거와 **켜기 전에 사람이 정해야 하는 것**은 [CREDITS.md](CREDITS.md) 에 있다.

`FEATURES.credits` 는 여전히 false 다. 기술적 장애가 아니라 유효기간·세무·
현금성 전환 여부라는 **정책 결정 셋이 남아서**다.

### 운영자 API

`ADMIN_TOKEN` 을 정해야 열린다. 없으면 404 로 존재 자체를 숨긴다.

| 경로 | 용도 |
|---|---|
| `GET /api/admin/held` | 보류된 기여 — 사람이 봐야 하는 것 |
| `POST /api/admin/release` | 보류 해제 후 지급 |
| `GET /api/admin/issuance` | 발행 현황과 규제선 대비 비율 |
