# 서버 이전 체크리스트

> 지금은 **서버가 없다.** 모든 상태가 기기 안(AsyncStorage)에 있고, 모든 판정이
> 클라이언트에서 일어난다. 정보 제공만 하는 현재 단계에서는 이걸로 충분하다.
>
> 이 문서는 **어디를 서버로 옮겨야 하는지**를 미리 표시해 둔 것이다. 개발은 하지 않았다.
> 각 항목에 「지금 상태 → 옮겨야 하는 이유 → 옮길 때 무엇을 서버가 맡는가」를 적는다.

## 한눈에

|---|---|---|---|---|

| 2 | 기여 교차검증 | `lib/contributions.ts` | 🔴 높음 | `FEATURES.credits` |
| 3 | GPS 인증 판정 | `lib/reviews.ts` | 🟠 중간 | 리뷰 공유 시 |

## 1. 크레딧 원장 🔴

**지금** — `loadProfile()` / `award()` 가 AsyncStorage의 `profile:v1` 을 직접 읽고 쓴다.
잔액도 누적 획득량도 기기 안에만 있다.

**왜 옮겨야 하나** — 저장소를 직접 고치면 크레딧을 무한히 만들 수 있다. 크레딧은 eSIM·
티켓 할인으로 교환되는, 즉 **금전적 가치가 있는 잔액**이다. 클라이언트가 자기 잔액을
계산하는 구조로는 절대 켜면 안 된다.

**서버가 맡을 것**
- 잔액·누적 획득의 유일한 사본(single source of truth)
- 지급/차감을 추가 전용 원장(append-only ledger)으로 기록 — 사후 감사 가능해야 한다
- 교환(`redeem`)은 멱등 처리 — 네트워크 재시도로 이중 차감이 나면 안 된다

**클라이언트에 남길 것** — 표시용 캐시. 화면이 잠깐 옛 잔액을 보여주는 건 괜찮다.

---

## 2. 기여 교차검증 🔴

**지금** — `confirmContribution()` 이 로컬 배열의 카운터를 올리고, 임계치에 닿으면
`status`를 `confirmed` 로 바꾸며 크레딧을 지급한다. **같은 기기에서 자기 제보를 자기가
확인할 수 있다.** 지금은 단일 기기 시뮬레이션이라 그렇게 열어 뒀다.

**왜 옮겨야 하나** — 교차검증은 "다른 사람이 확인했다"는 사실 자체가 전부인 장치다.
그 판정이 제보자 기기 안에 있으면 아무 의미가 없다.

**서버가 맡을 것**
- 제보자 ≠ 확인자 강제, 확인자 1인 1회 제한
- 확정 판정과 그 시점의 크레딧 지급 (원장과 같은 트랜잭션 안에서)
- 등급별 요구 확인 수 계산 — `confirmationsRequired()` 를 서버로 옮긴다
- 반려 누적 시 제재 (현재 설계에 없음. 추가 필요)

**남는 문제** — 여러 계정을 만들어 서로 확인해 주는 담합은 이 구조로 못 막는다.
계정 생성 비용(전화번호 인증 등)과 이상 패턴 탐지가 별도로 필요하다.

## 3. GPS 인증 판정 🟠

**지금** — `checkProximity()` 가 기기에서 거리와 정확도를 계산해 통과 여부를 정한다.

**왜 옮겨야 하나** — 앱을 거치지 않고 API를 직접 호출하면 "인증됨" 상태를 그냥 만들어
보낼 수 있다. 리뷰가 내 기기에만 남는 지금은 무해하지만, 남에게 보이는 순간 문제가 된다.

**서버가 맡을 것**
- 좌표·정확도를 받아 **서버가 다시 판정**한다. 클라이언트 판정 결과는 참고만 한다
- 장소 좌표와 `radiusM` 은 서버 데이터를 기준으로 한다 (앱 내장본은 표시용)
- 같은 사용자가 짧은 시간에 멀리 떨어진 두 곳을 인증하면 거부 — 물리적으로 불가능한
  이동은 위치 위조의 가장 잡기 쉬운 신호다

**주의** — 서버로 옮겨도 모의 위치 앱은 못 막는다. 판정 위치를 옮기는 것은 *API 우회*를
막는 것이지 *위치 위조*를 막는 게 아니다. 둘은 다른 문제다.

---

## 4. 리뷰 저장소 🟠

**지금** — `reviews:v1` 키에 로컬 저장. 앱을 지우면 사라지고, 남에게 보이지 않는다.

**서버가 맡을 것**
- 리뷰 CRUD, 장소별 집계(`aggregate()` 의 서버판)
- 신고·삭제 처리
- **인증 리뷰만 평균에 반영**하는 규칙은 서버에서 강제한다. 이 앱 평점의 존재 이유다

---

## 5. 지진 푸시 알림 🟠

**지금** — `use-quakes.ts` 가 60초마다 P2PQuake `/history` 를 폴링한다. 앱이 백그라운드로
가면 멈춘다.

**왜 옮겨야 하나** — 앱을 켜야만 지진을 아는 구조는 위급 정보로서 쓸모가 없다.
긴급지진속보는 흔들림 도달 전 수 초~수십 초가 전부다.

**왜 클라이언트가 직접 못 하나** — P2PQuake WebSocket(`wss://api.p2pquake.net/v2/ws`)은
**IP당 동시 2연결** 제한이 있다. 사용자마다 직접 붙을 수 없다.

**서버가 맡을 것**
- WebSocket **1개 연결**로 구독 → 이벤트를 받아 저장
- 사용자의 체류 도도부현과 대조해 대상자만 추려 Expo Push 로 팬아웃
- 진도 임계치(예: 진도 4 이상)와 EEW는 다른 채널로 — 모든 지진을 알리면 알림을 꺼 버린다
- 폴링은 WebSocket 끊김 대비 fallback 으로 유지

## 6. 큐레이션 데이터 배포 🟡

**지금** — 공항·패스·장소가 전부 앱에 하드코딩. 요금이 바뀌면 **앱을 새로 배포해야 한다.**

**옮길 때** — 서버에서 JSON 을 내려받아 캐시하고, 앱 내장본은 **오프라인 fallback** 으로
남긴다. 공항 화면이 데이터 로밍 없이 열리는 건 이 앱의 장점이라 없애면 안 된다.

관련: `data/transit.ts` 의 `verified` 플래그와 `PASS_CHECKED_AT` — 서버로 옮기면
확인 시점을 항목별로 관리할 수 있다.

## 7. 장소 데이터 확장 🟡

**지금** — 손으로 적은 30여 곳.

**옮길 때** — Google Places 등으로 후보를 넓히되 `Place` 스키마로 정규화해 들어온다.
무료 한도가 SKU별로 나뉘므로(Essentials 10K/월, Pro 5K/월) **서버 캐싱이 먼저**다.
클라이언트가 직접 Places 를 부르면 키가 노출되고 한도가 순식간에 소진된다.

## 코드에서 찾는 법

서버로 옮겨야 하는 지점은 소스 주석에 이유와 함께 적혀 있다.

```bash
grep -rn "서버" src/lib/ src/hooks/
```

## 먼저 정해야 할 것

서버를 붙이기 전에 답이 필요한 것들이다. 기술 선택보다 이게 먼저다.

1. **계정을 만들 것인가** — 리뷰를 공유하는 순간 필요해진다. 소셜 로그인만으로 갈지,
   전화번호 인증까지 받을지에 따라 어뷰징 방어 수준이 갈린다.
2. **위치를 서버에 보낼 것인가** — 인증 판정을 서버로 옮기면 사용자 위치가 서버에 남는다.
   개인정보 처리방침과 보관 기간을 먼저 정해야 한다.
3. **크레딧의 법적 성격** — 현금성 포인트로 보이면 규제 대상이 될 수 있다. 기프티콘
   전환을 넣는다면 이 검토가 선행되어야 한다.
